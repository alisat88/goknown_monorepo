# DAppGenius activity ledger — Phase 1

Status: local implementation, disabled by default. No production migration,
role provisioning, deployment, commit, or changes to existing authorization.
Base: `78dfac9b5d46e3f7344113febe2ca51910bb1609`, equal to the locally available
`origin/main` at implementation start. No remote fetch or review-status claim.

## Coverage and interpretation

This is **best-effort authenticated in-app DigitalAssets preview telemetry**.
The reported metric is **ESTIMATED ACTIVE PREVIEW TIME**, never proven human
attention, reading, playback duration, or an every-access audit guarantee.

Only the preview page attaches the session hook, after metadata authorization
and viewer readiness. Image readiness comes from the actual rendered image load
with nonzero natural width; video/audio use `loadeddata`; PDFs use successful
page rendering. Lists, thumbnails, metadata/conversion polling, unsupported
viewers and failed initial loads do not start sessions. Ready previews opened
by navigation or a direct preview-page link count as deliberate preview-page
visits. There is no attempt to prove a physical human initiated that navigation.
A client can forge readiness/visibility reports; server bounds limit estimates,
not prove honest behavior. Audio loadeddata is readiness, not playback.
Browser data-saving behavior or unsupported readiness signals can undercount.

Existing `/files` and public object-storage content URLs remain unchanged.
Direct bytes, external viewers, cached copies, browser downloads and forwarding
of URLs are not attributable by this milestone. No changes were made to private
asset ownership checks, folder/group grants, strict sessions, token expiration,
legacy JWT behavior, or download authorization. Sharing discrepancies and direct
URL attribution gaps from the investigation remain separate work.

The server calls the existing `FindDigitalAssetsService.execute(assetSyncId,
verifiedJwtSubject)` on start and every client mutation, including replays. It
resolves both local primary IDs and sync IDs itself. Nonexistent assets are
rejected. The session must belong to that resolved actor and asset. Read access
is the current actor's history only (including assets no longer viewable); no
owner/admin/organization-wide activity access is introduced.

## Flags and contracts

Both flags default off:

- Backend: `ACTIVITY_LEDGER_ENABLED=true` (literal string only).
- Frontend build: `REACT_APP_ACTIVITY_LEDGER_ENABLED=true`.
- Backend: `ACTIVITY_LEDGER_SOURCE_NODE`, stable nonsecret node identifier,
  `[a-zA-Z0-9_.-]{1,64}`. Defaults to `local` for development; assign a distinct
  deployment origin before a multi-node rollout. Never use a hostname containing
  credentials or an arbitrary environment dump.

Disabled backend endpoints return 404 without touching the database. Existing
asset endpoints and Audit Logs are unchanged. All enabled endpoints use the
existing bearer authentication middleware:

| Method/path | Body/query |
| --- | --- |
| POST `/me/activity/assets/:assetSyncId/access-sessions` | `{ "request_id": "client-generated-random-uuid" }` |
| POST `/me/activity/assets/:assetSyncId/access-sessions/:sessionId/heartbeat` | `{ "sequence": 1, "elapsed_ms": 15000, "reason": "heartbeat" }` |
| POST `/me/activity/assets/:assetSyncId/access-sessions/:sessionId/end` | `{ "sequence": 2, "elapsed_ms": 1000, "reason": "navigation" }` |
| GET `/me/activity/events` | `limit` (1–100; default 50), optional paired `before_at` ISO UTC milliseconds and `before_id` UUID |

End reasons: `hidden`, `offline`, `idle`, `navigation`, `pagehide`, `error`,
`sleep`. Timeout is generated by the server only. Extra body/query fields are
rejected. There is no caller-supplied actor ID, asset metadata, duration total,
client timestamp or arbitrary event type. Observations are integer elapsed
samples, not trusted durations. Maximum input elapsed is 24 hours; any interval
above 20 seconds receives zero credit, never a capped credit across a long gap.

Successful writes return 200 with `id`, `access_session_id`, `sequence`,
`event_type`, `recorded_at`, `outcome`, `metadata`. Start sequence is zero. IDs
and recorded timestamps are generated by PostgreSQL. Exact replays return the
original event. Different data at the same sequence, out-of-order observations,
ended sessions and expiry return 409. Invalid input returns 400; nonexistent or
foreign sessions return 404. Preview authorization retains its existing errors.
Unexpected persistence errors return sanitized 503. The actor rate limiter is
180 requests/minute/process, not a global distributed quota.

Reads return `{ events, incomplete_sessions, next_cursor, measurement, coverage }`. The cursor is a
`{ before_at, before_id }` pair or null. Events contain only the public envelope;
internal replay fingerprints are omitted. A full page can have a next cursor
whose subsequent page is empty. Pagination is descending by `(recorded_at,id)`;
timestamp precision is milliseconds to match the JSON cursor exactly.

## Immutable event storage and concurrency

Migration: `1792000000000-CreateActivityLedger.ts`, following the existing
`1791800002000` migration. It uses the parent's existing `uuid_generate_v4()`
prerequisite; it does not install extensions or provision production roles.

`activity_events` has a UUID ID, schema version, allowlisted event type,
DB timestamp, actor primary/sync IDs, asset primary/sync IDs, source node,
server-generated access session ID, correlation UUID, sequence, controlled
outcome, internal SHA-256 request fingerprint and bounded JSON metadata.
Metadata keys are exactly `estimated_active_ms`, `reason`, `measurement`, bounded
at 512 bytes in the DB. There are no filenames, content URLs, raw documents,
request/response dumps, tokens, credentials, IP addresses, emails or user names.
Historical identity is a snapshot: no cascading or SET NULL foreign keys.

`activity_access_sessions` is a mutable coordination projection. It contains
identity, request ID, last sequence/time and ended state. It is not historical
truth. Every accepted observation and projection change commits in one database
transaction. UNIQUE actor/request keys serialize concurrent starts; row locks
serialize mutations across processes; event session/sequence uniqueness and a
single-end partial unique index provide further protection. A content hash of
normalized allowlisted observation fields detects conflicting retries. All SQL
values use parameters. A failed event insert rolls back projection changes.

The legacy Audit Logs writer, schema/API, BFT, financial records, ZTA Coin,
KnownCompute, groups and sharing paths are not reused or changed.

## Timing policy

- Heartbeat target: 15 seconds. Accept a credited interval only if both server
  elapsed and client monotonic elapsed are within 0–20 seconds; credit the
  smaller value, rounded down. The 5-second allowance tolerates modest scheduler
  jitter without crediting long sleeps. No HTTP response latency is used as a
  viewing duration.
- Heartbeats require visible, online, viewer-ready state and recent interaction.
  Pointer/key/scroll/touch activity refreshes the 60-second idle threshold.
  Reading without input, accessibility interactions not covered by these events,
  and background audio can undercount. Playback is not measured separately.
- Hide, navigation and pagehide attempt an end, with only the bounded tail.
  The backend conservatively assigns zero credit to offline, idle, sleep, error,
  hidden and pagehide observations regardless of client-reported elapsed time.
  A resumed foreground segment gets a fresh session; tabs are independent.
- An 8-second request deadline and one identical sequential retry bound network
  waiting. Failures stop that capture lifecycle with a sanitized console warning;
  they never fail the viewer. A later visibility/readiness lifecycle can retry.
- Close uses authenticated `fetch` with `keepalive`, never a credential-less
  beacon or tokens in URLs. The browser may still drop it. A start in flight may
  not be acknowledged before unload, and a queued close may never run.
- Server expiry: 45 seconds since the last accepted observation. An expired
  session cannot accept further observations. History reads remain read-only and
  expose stale open projections in `incomplete_sessions` with reason `timeout`
  and zero additional credit. A separately approved maintenance process may
  later append a terminal timeout event; this Phase 1 request path does not do so.
  Until then an open row older than 45 seconds is logically incomplete. Its
  duration ends at the last credited observation, not at discovery time.
  The timeout representation records server inference about the original actor's
  session; it does not assert that actor performed a close.

To derive one session's estimate, sum its accepted event interval credits.
For a per-actor/per-asset cross-tab total, reconstruct intervals
`[recorded_at - estimated_active_ms, recorded_at]` and take their union, using
`unionIntervalMs` over a **complete** set. Do not sum overlapping tab totals or
label one paginated page as a total. The read API deliberately exposes no
aggregate. Delay/jitter can shift interval placement; these remain estimates.
No historical backfill is possible from metadata GETs or old audit logs.

## Database privilege prerequisite and rollout

The migration rejects UPDATE, DELETE and TRUNCATE using a BEFORE STATEMENT
trigger, even for a normally privileged writer. Meaningful protection also
requires a non-owner runtime role. Before any production enablement, separately
review/configure the following (nothing here was provisioned in production):

1. A migration role owns the new tables/function. The application runtime role
   must not own the database, schema, tables or trigger function, be a superuser,
   inherit the owner role, or have DDL/trigger-disabling/replication privileges.
2. Grant runtime SELECT/INSERT on `activity_events`, and SELECT/INSERT/UPDATE
   on `activity_access_sessions`; no event UPDATE/DELETE/TRUNCATE, no projection
   DELETE. Existing application-table privileges must be preserved, not broadly
   revoked by an automated script. Verify effective inherited privileges.
3. Keep migrations out of application startup and never grant migration-owner
   credentials to the web process. Confirm uuid-ossp exists, migration ordering,
   default privileges and the actual restricted-role tests in staging.
4. Apply the additive migration via the approved release process, deploy backend
   with capture off, then frontend with capture off. Enable a small cohort only
   after authorization, privacy, volume and operational review.
5. Monitor sanitized capture failures/503s, expired-session ratio, event volume,
   and write latency. An active tab produces about four heartbeat rows/minute.
   No peer-node replication fanout is added; all coordinating instances must
   use the same authoritative PostgreSQL database. Independent node databases
   need a separately designed idempotent transport before a global ledger claim.

Database administrators can bypass triggers or rewrite/restore the database.
This is not cryptographic evidence against privileged tampering. Optional future
signed checkpoints must be anchored outside this database under independent
control; an internal hash chain alone is insufficient.

Rollback: disable frontend capture and backend flag; keep the additive tables
and recorded history. Migration `down()` intentionally refuses destructive
rollback. Do not TRUNCATE or drop the table to uninstall. Projection cleanup and
retention require a separately approved policy; no automatic retention deletion
or backfill runs here. Historical IDs are personal data even without names.

For future fail-closed requirements, gate **content delivery**, not just telemetry
POSTs, on durable events; reconcile direct URLs/caches, private delivery,
transactional grant checks, authorization revocation and outage behavior first.
That is a separate product/security phase, not an enabled option in this code.

## Reuse in later phases

Phase 2 API actions can reuse the append writer, identity resolution, versioned
allowlists, idempotency and actor-scoped pagination. Add operation-specific
service events only after successful commit; do not count polling, background
jobs or node sync as humans. Add caller classification and generic resource
fields through an additive migration; retain existing asset rows unchanged.

Phase 3 group/membership events must join the same transaction as actual
creation/membership changes. Distinguish sharing groups, organization groups and
rooms, Messenger groups, pending invitations and accepted/active membership.

Phase 4 sharing events must record actual grant/revoke diffs and recipient IDs,
not entire forms/folders or asset content. New event types/schema versions need
explicit validators and DB check updates; this phase accepts none of them yet.
